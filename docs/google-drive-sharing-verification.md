# Family Tree 共享项目访问验证

目的：定位接收方无法打开本应用创建的共享家谱，是账号或文件共享权限、OAuth 文件范围、项目查询，还是项目内容校验导致。当前“应用里看不到”作为已报告现象记录，无需用户反复尝试相同操作。

接收方在 Drive 网页可读已由用户确认。验证以开发者构造的虚构项目为主，不要求用户提供私人链接。权限组合的一手实践见 [研究记录](research/google-drive-shared-project-access.md)。

## 测试准备

- A 为创建者，B 为接收共享的账号；使用同一部署网站和同一 OAuth 应用，分别用两个浏览器配置文件登录，避免混用账号。
- 优先使用 A 在 Family Tree 创建的虚构家谱，包含一个成员和一张测试照片，并确认保存完成。已有失败文件夹可以作为对照，但不把真实家谱内容放进日志或仓库。
- A 在 Google Drive 中将整个项目文件夹明确共享给 B。第一轮使用查看权限，避免无意写入；编辑权限另测。
- 记录网站地址和目标文件夹 ID。确认 B 在 Drive 网页能打开该文件夹及里面的版本、照片；网页可读证明用户权限，不证明 Family Tree token 有权限。
- 若 OAuth 应用处于 Testing，B 必须具备测试用户资格。若已能连接并读取账号，可继续检查文件请求，不把所有失败都归因于测试用户配置。
- 对照基线 aa26cec 的 scope 为 drive.file；本次实现为 drive.file 加 drive.readonly。需要记录新授权回调中的实际 scope 集合；缓存中的配置 scope 不能证明 Google 实际返回的授权集合。不要打印 token、完整 OAuth 回调、Authorization 请求头或导出未脱敏 HAR。
- 不使用另一个 API Explorer、ChatGPT Drive 插件或其他 OAuth 客户端代替此网站，否则无法验证当前应用的逐文件访问范围与私有项目标记。

## 同一应用内的只读检查

开发者在 Family Tree 的同一账号连接内部执行以下探针，复用现有 token，只输出状态与检查结果。不要让用户复制访问令牌。浏览器 Network 可先查看现有项目列表请求；指定 ID 的探针需要开发诊断入口，不是现有用户功能。

| 检查 | 请求或操作 | 记录内容 |
| --- | --- | --- |
| 账号 | 现有 about 用户请求及页面账号显示 | 是否为 B；不记录 token |
| 列表 | 现有 listProjects 查询，走完分页 | HTTP 状态、目标 ID 是否出现、incompleteSearch |
| 指定目录 | files.get，指定已知的项目文件夹 ID | HTTP 状态、mimeType、familyTree/kind 标记、isAppAuthorized、canAddChildren/canRename |
| 子文件 | files.list，以目标 ID in parents 且 trashed=false 查询；诊断时先不加 appProperties 过滤 | 是否出现预期版本、主图和缩略图，其项目标记是否可见 |
| 内容读取 | 对一个已知版本 JSON、一张主图及对应缩略图分别 GET alt=media | HTTP 状态、是否能完整读完；不输出文件内容 |
| 应用打开 | 使用现有存储提供商 loadProject 和 readPhoto 路径 | 成功，或具体的格式/历史/照片错误类别 |

版本与照片 ID 由 A 的成功访问确定。B 的子文件列表为空时，仍应直接检查这些已知 ID，区分“列表没返回”和“文件本身不可读”。A 也执行相同探针作为对照，证明 ID 和项目本身有效。

错误记录只包含 HTTP 状态、Google 错误 reason、检查阶段和必要的布尔结果。404 也可能隐藏无权访问，不能直接解释为文件已删除；isAppAuthorized 是辅助信息，不能替代实际读取结果。

## 单变量授权对照

若网页共享权限正常、Family Tree 的原始 API 读取受限，使用同一个 OAuth Client ID 的测试构建，将授权范围改为 drive.file 加 drive.readonly，再重复上述只读探针。新范围同时登记在 Google 控制台；应用的授权校验和缓存恢复也必须按 scope 集合处理，不能只改控制台或强行复用旧 token。

此对照保持账号、文件夹、项目内容和查询条件不变，只改变 scope。使用没有残留完整 drive 授权的测试账号或可控测试授权状态。不要为清理对照而撤销真实生产账号的其他应用连接。

| 结果 | 结论与下一步 |
| --- | --- |
| B 在 Drive 网页也不可读 | 先修正共享对象或 Google 账号，当前证据不足以归因于 OAuth |
| drive.file 受限，增加 drive.readonly 后同一请求成功 | 支持 OAuth 范围是该读取失败的原因，按最小组合推进 |
| 指定目录可读且标记正常，完整列表没有目标 | 检查查询、分页、搜索可见时序和前端列表处理 |
| 目录可读但 appProperties 缺失 | 对照 A 的结果及实际 OAuth 应用身份，不能直接丢弃项目标记校验 |
| 目录可读但版本或照片不可读 | 检查逐文件范围、继承权限、文件位置及对应 API 响应 |
| 原始内容读取成功，应用打开失败 | 检查项目格式与版本图校验，继续扩大 scope 没有依据 |
| 两组 scope 下都失败 | 保留具体状态和错误 reason，继续定位，不能据此直接跳到完整 drive |

## 完成标准与后续

真实验收完成需要一张真实结果表，列出 A 与 B、drive.file 与双 scope、目录与版本及照片的结果，指出失败边界。模拟测试通过不能作为本步骤的完成依据。

只有读取原因明确后，再在虚构项目上将 B 改为编辑者，测试新增快照、上传照片和重命名；最后由 A 重新读取确认。这些写入结果决定是否需要进一步处理应用逐文件授权。当前检查不更改生产权限、不迁移项目、不写入真实家谱。
